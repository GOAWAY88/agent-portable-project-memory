# APMF V0.3: Project Profiles

Status: experimental. V0.3 extends V0.1/V0.2; it does not change the canonical Markdown model, the four-artifact change lifecycle, provenance rules, or status vocabularies.

## Motivation

Different projects keep different durable truth. A software project centers on architecture and verified commands; a research/paper project centers on research questions, methods, and an experiment ledger with data versions, seeds, and environment commits. The protocol stays domain-neutral; the seeded knowledge set becomes declarative.

## Profile contract

An APMF V0.3 profile is a directory `template/profiles/<name>/` containing:

- `profile.md`: a manifest with front-matter `name` (matching `^[a-z][a-z0-9-]*$`) and `required_knowledge` (space-separated `.md` filenames);
- `INDEX.md`: a profile-specific router seed for `.ai/INDEX.md`;
- `knowledge/`: seed documents for `.ai/knowledge/`.

A profile name MUST match `^[a-z][a-z0-9-]*$`. Because that pattern admits no `/` and no `.`, a name can never traverse outside `template/profiles/`; values such as `..`, `../paper`, `paper/..`, and `BadName` MUST be rejected before any file is written. A profile directory MUST contain all three of `profile.md`, `INDEX.md`, and `knowledge/`; an incomplete profile MUST be rejected with a diagnostic naming the missing member.

`init.sh --profile <name>` MUST install the shared core, then the profile overlay, and MUST write the manifest to `.ai/profile.md` in the generated project. An unknown or invalid profile name MUST fail with a clear error listing available profiles. Default profile is `software`, preserving pre-V0.3 behavior.

Every file copy MUST be checked: a failed copy MUST cause a non-zero exit, and an implementation MUST NOT report a file as created when the copy failed. The message asserting that a profile was applied MUST be emitted only after every overlay file has been successfully created or confirmed identical.

## Overlay conflicts and idempotence

The profile overlay determines which profile a project *is*, so it MUST be applied atomically. Before writing anything, an implementation MUST preflight the overlay and classify each destination as absent, byte-identical to the profile seed, or differing.

- A destination that is byte-identical to its seed is an idempotent success and MUST NOT be rewritten.
- A destination that exists with differing content is a conflict. Conflicts MUST be reported individually, MUST NOT be overwritten, and MUST cause a non-zero exit with **no** overlay file written, so a failed run cannot leave a partially applied profile.
- If `.ai/profile.md` already exists and declares a different profile name, that MUST be reported as a conflict and MUST fail, even when no other overlay file differs.

An implementation MUST NOT report that a profile was applied when the resulting manifest declares a different profile. Re-running `init.sh --profile <name>` on a project already initialized with `<name>` MUST succeed and leave the tree unchanged.

The shared core (`.gitignore`, `AGENTS.md`, and the common `.ai/` scaffolding) keeps the V0.1 behavior of preserving existing files, reporting conflicts, and exiting zero, because it is idempotent boilerplate rather than profile identity.

## Validation rules

A V0.3 validator MUST fail when:

- `.ai/profile.md` exists but its `name` is malformed or `required_knowledge` is missing/empty;
- a `required_knowledge` entry is not a plain `.md` filename — that is, it does not match `^[A-Za-z0-9][A-Za-z0-9._-]*\.md$`, which excludes `/`, `..` traversal, absolute paths, and non-Markdown suffixes;
- a `required_knowledge` entry names a file absent from `.ai/knowledge/`.

The list MUST be split without shell glob expansion, so a value such as `*.md` cannot be expanded into existing filenames before it is checked. Required knowledge MUST always resolve inside `.ai/knowledge/`; a manifest MUST NOT be able to satisfy the contract with a file outside that directory.

When `.ai/profile.md` is absent, the validator MUST fall back to the frozen software defaults (`PROJECT.md`, `ARCHITECTURE.md`, `COMMANDS.md`), so projects initialized before V0.3 keep validating unchanged.

## Boundaries

- Profile selection is explicit and human-driven. Tooling MAY suggest a profile from repository signals but MUST NOT decide silently; the installed manifest is the recorded provenance of the choice.
- Editing `required_knowledge` is a normal memory update: the manifest and the knowledge tree MUST stay consistent, enforced by validation.
- The frozen V0.1-alpha contract requires the `.ai/knowledge/` directory, not specific filenames; profiles do not alter the baseline. Changes to the default required set of the `software` profile are compatibility-relevant and SHOULD be recorded as an ADR.
- No retrieval layer, database, or agent-specific hook is introduced; profiles are plain tracked files.
